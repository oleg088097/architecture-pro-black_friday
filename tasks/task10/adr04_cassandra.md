### <a name="_3bfxc9a45514"></a>**Контекст**

Коллекция **orders**:
```mongodb-json
{
    "_id": ObjectId, 
    "user_id": String, 
    "order_date": Date, 
    "items" : [{
        "product_id": ObjectId,
        "price": Integer
    }], 
    "status": String, 
    "total_price": Integer,
    "geo_zone": String,
}
```
Основные операции:
- Быстрое создание заказов с одновременным списанием остатков.
- Поиск истории заказов конкретного пользователя.
- Отображение статуса заказа.


Коллекция **products**:
```mongodb-json
{
    "_id": ObjectId, 
    "display_name": String,
    "category": String,
    "price": Integer, 
    "stock" : [{
        "geo_zone": String,
        "quantity": Integer
    }], 
    "attributes": JSONB
}
```
Основные операции:
- Частые обновления остатков при покупках.
- Поиск товаров по категориям и фильтрация по диапазону цен.
- Описание товара на странице продукта.


Коллекция **carts**:
```mongodb-json
{
    "_id": ObjectId, 
    "user_id": String,
    "session_id": String,
    "items": [{ "product_id": ObjectId, "quantity": Integer }],
    "status": String,
    "created_at": Date,
    "updated_at": Date,
    "expires_at": Date
}
```
Основные операции:
- Создание корзины, когда заходит гость или новый пользователь.
- Получение текущей корзины по фильтру { session_id, status:"active" } или { user_id, status:"active" }.
- Добавление или замена товара в корзине.
- Удаление товара из корзины.
- Слияние гостевой корзины в пользовательскую, если пользователь залогинится:
    - прочитать гостевую { session_id, status:"active" };
    - добавить её items в корзину { user_id, status:"active" };
    - отметить гостевую как abandoned.
- Отметка корзины как заказанной.

### <a name="_qmphm5d6rvi3"></a>**Решение**

#### Стоит перенести в Cassandra:
- Активные заказы - геораспределённые данные, часто создаются и читаются одним пользователем, требуется высокое масштабирование и нет ожиданий высокой консистентности
- Корзины - геораспределённые данные, часто обновляются и читаются одним пользователем, требуется высокое масштабирование и нет ожиданий высокой консистентности
- Пользовательские сессии - геораспределённые данные, часто обновляются и читаются одним пользователем, требуется высокое масштабирование и нет ожиданий высокой консистентности

#### Не стоит переносить в Cassandra:
- История заказов - геораспределённые данные, но обращения к ним происходят реже, не требуется масштабирование. 
- Товары - эта сущность требует высокой масштабируемости, но она должна быть консистентной, т.к. к ней обращается больше кол-во клиентов и проблемы с консистентностью могут привести к продаже несуществующего товара. Однако, если найти решение данной проблемы (например разделить модель товара, осуществлять возврат средств, управлять этим через статусную модель заказа), то можно улучшить доступность товаров. 

#### CQL

Активные заказы:
- Partition Key: требуется распределить по геозонам, далее по user_id для распределения данных.
- Clustering Key: упорядочим заказы по дате для более простого получения упорядоченной выборки.
```cassandraql
CREATE TABLE active_orders (
  id                    INT,
  user_id               UUID,
  order_date            TIMESTAMP,
  items                 list<tuple<VARCHAR, INT>>,
  status                VARCHAR,
  total_price           INT,
  geo_zone              VARCHAR,
  PRIMARY KEY ((geo_zone, user_id), order_date)
);
```

Корзины:
- Partition Key: требуется распределить по геозонам, далее по user_id/session_id для распределения данных. Но cassandra в отличие от mongodb не поддерживает null для Partition Key, потому объединим эти два поля в одно user_session_id.
- Clustering Key: упорядочим корзины по статусу для приоритетного получения активных корзин.
```cassandraql
CREATE TABLE carts (
  id                    INT,
  user_session_id       UUID,
  items                 list<tuple<VARCHAR, INT>>,
  status                VARCHAR,
  created_at            TIMESTAMP,
  updated_at            TIMESTAMP,
  expires_at            TIMESTAMP,
  geo_zone              VARCHAR,
  PRIMARY KEY ((geo_zone, user_session_id), status)
);
```

Пользовательские сессии:
- Partition Key: требуется распределить по геозонам, далее по user_id/session_id для распределения данных. Но cassandra в отличие от mongodb не поддерживает null для Partition Key, потому объединим эти два поля в одно user_session_id.
```cassandraql
CREATE TABLE carts (
  id                    INT,
  user_session_id       UUID,
  created_at            TIMESTAMP,
  data                  VARCHAR,
  geo_zone              VARCHAR,
  PRIMARY KEY ((geo_zone, user_session_id))
);
```

#### Cтратегии целостности данных
Активные заказы:
- Hinted Handoff - возможно обновление не будет прочитано и восстановлены Read Repair, требуется 
- Anti-Entropy Repair - вне рабочих часов для полной синхронизации

Корзины:
- Read Repair - корзины часто читаются, починка будет произведена при чтении
- Anti-Entropy Repair - вне рабочих часов для полной синхронизации

Пользовательские сессии:
- Read Repair - сессии часто читаются, починка будет произведена при чтении
- Anti-Entropy Repair - вне рабочих часов для полной синхронизации

### <a name="_bjrr7veeh80c"></a>**Последствия**

Миграция на Cassandra позволит повысить доступность и масштабируемость для данных, принеся в жертву гарантии консистентности. 

Это потребует изменения модели данных и их миграции, увеличения стоимости эксплуатации системы.

Статичные и реже читаемые данные останутся в кластере MongoDB. В этом же кластере должны останутся данные, для которых высокий приоритет имеет консистентность. Если потребуется улучшить показатели коллекции товаров, выше были предложены способы.
